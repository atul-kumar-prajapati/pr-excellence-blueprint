The why

A big, unclear PR doesn’t save time. It moves the risk.

Review friction

Big PRs wait. People postpone them, skim them, then approve under pressure.

Hidden risk

The dangerous five lines hide among five thousand. Nobody sees the migration for the formatting.

Cognitive load

Nobody can hold 63 files in their head. Reviewers fall back to style because that’s all they can process.

The cost of a bad PR is paid by everyone except the person who raised it.

Name the three costs. Then move.

The quality bar

A great PR makes the reviewer’s job easy and the release boring.

Must-haves

  • One clear purpose
  • Small enough to review properly
  • Evidence for every claim
  • Tests that check behaviour, including failures
  • No security or data-integrity red flags
  • A way to roll back — including data

Nice-to-haves

  • Diagrams for complex flows
  • Performance numbers when the path isn’t hot
  • A polished commit history
  • Screenshots for UI changes

Nice-to-haves never compensate for a missing must-have.

Each must-have maps to a section of the template.

Size is the first quality bar

#4127 should have been four PRs

PR 1

Refactor

~300 lines. No behaviour change, proved by existing tests.

PR 2

Additive migration

~40 lines. New nullable columns. Old and new code both work.

PR 3

Feature behind a flag

~350 lines. Off by default. Tests and evidence.

PR 4

Clean-up

~120 lines. Remove the flag and tighten constraints.

If you can’t explain your PR in one sentence, it’s more than one PR.

Expand then contract is what makes the migration safe.

Anatomy of a great PR

Meets the expectations — and shows the evidence that proves it.

1 · Intent

What changed, and why?

Title, ticket, What changed?, Why?

2 · Merge

Is it correct, tested and safe?

Verification, tests, checklist. Correctness, testing, maintainability, security.

3 · Release

Will it go out safely?

Impact, linked PRs. Data integrity, compatibility, operability.

Every claim has evidence attached — or says honestly why it doesn’t.

Three questions every reader asks.

Intent clarity

What changed, and why — in one read

Before
fix discount bug

Fixed the discount issue. Tested locally.
After
fix(pricing): round promo discounts to 2dp
using HALF_EVEN (#231)

Why: finance flagged totals like 212.0749999.
Rule agreed with finance (FIN-12).
Risk: Medium — checkout totals and invoices.
No schema or API change.

The risk line is the cheapest improvement most teams can make.

Merge confidence

Is it correct, tested and safe?

Tests that prove behaviour

Runs the code
assertNotNull(result);
Proves the rule
assertThat(result)
  .isEqualByComparingTo("212.08");

Security at the boundary

Any user, any booking
return service.findById(id);
Ownership checked
return service.findForUser(id, user.id());

Nothing sensitive in logs

PII in INFO
log.info("Booking for {} <{}>", name, email);
Identifiers only
log.info("Booking {} for user {}", id, userId);

“Not run, and why” and “Not tested, and why” are features, not confessions.

Spend time on honest gaps.

Release certainty

Will it go out safely — and come back safely?

Fails on existing rows
ALTER TABLE booking
  ADD COLUMN payment_reference
  VARCHAR(64) NOT NULL;
Breaks web and mobile
- List<String> seatNumbers,
+ List<String> seats,
Retry without idempotency
paymentClient.charge(user, total);

Reverting code doesn’t revert a migration, a renamed field or a double charge.

Expand-then-contract. Old and new code must both work during a rolling deploy.

One yardstick

Merge confidence score

5 Merge now

4 Minor nits

3 Some risk, not blocking

2 Blocking issues

1 Rethink or split it

Gating rules

Any red on security, data integrity or rollback caps the score at 2.

A claim without evidence caps the score at 3.

An AI score is advisory. The human reviewer’s score is final.

From findings to principles

Five things we don’t compromise on

As an author

One purpose per PR

If you can’t explain it in one sentence, split it.

No claim without evidence

Show the test, the log or the CI result. “Tested locally” is not evidence.

Make it reversible

Plan compatibility and rollback from the start — including data.

As a reviewer

You own what you approve

Only approve what you’d be willing to defend. Read the deleted lines too.

Be clear and kind

Label every comment: blocker, suggestion, nit or question. Review the code, not the person.

Build these from the lab, then reveal.

Using AI to raise great PRs

We use AI to raise great PRs, but we own everything that goes in.

Intent

Draft What changed? and Why? from the diff. Flag anything the ticket didn’t ask for.

Merge

Self-review against the checklist. Find weak tests. Propose a 1–5 score with reasons.

Release

Check migrations, API changes, config, logging. Draft rollout and rollback.

AI raises the floor. Knowing what great looks like comes first.

Nothing new to learn — AI checks the same bar faster.

Where AI goes wrong

Plausible is not the same as correct

It makes the 5,000-line PR easy

Generating code is cheap. Reviewing it is not.

Tests that check nothing

Happy to write assertNotNull — or a test that locks in the bug, like PR B’s retry.

@Transactional on private

Compiles, reads well, does nothing.

It believes the description

Ask it to compare claims against the diff, not to summarise the description.

Never paste secrets or PII

Use fixtures and redacted logs.

Say when AI helped

Disclosure is about review focus, not blame.
