How to raise great PRs

You used to raise maybe two pull requests a week. With an agent next to you, twenty is normal. Volume went up. The bar did not move.

In an enterprise, especially on Java, “it works” is not a PR. It has to last. It has to stay fast. It has to stay compliant, maintainable, and secure. Other software will call yours, so you write it down. Other people will live with it, so you write for them.

Do that and you get claps. This is practice for that muscle.

Things to pick up, then we open a real PR

  1. If a stranger cannot tell what changed from the title, the reviewer is already behind. Type, scope, what happened. Not “fixes” and not “changes”.
  2. The purpose lives in the PR. A ticket link is extra, not a substitute. If they have to open Jira to know why this exists, the Why is missing.
  3. A product owner does not care that coverage went up. They care that checkout still totals correctly. If the test would pass on the old code, it is not evidence.
  4. Judge the production change, not a hard line-count. Tests can be longer than the code they protect. That is fine. If they have to scroll for twenty minutes through mixed unrelated files they will skim, then approve under pressure. That is how 5000-line PRs ship.
  5. Durable. Fast enough. Compliant. Observable. The person on call and the support engineer are part of this PR even if they never open GitHub.
  6. Do not spend review comments on formatting. Run the standards before you ask someone to read it. Review time is for design, correctness, and risk.
  7. If you say you tested it, show the test. If you did not run something, write that down and why. Video, logs, a command, a screenshot. Something a reviewer can look at without trusting your memory.
